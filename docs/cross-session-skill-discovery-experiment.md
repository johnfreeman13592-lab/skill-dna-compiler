# Cross-Session Skill Discovery 実験計画

策定日: 2026-07-23  
状態: 実装前の価値検証計画

## 1. 目的

メモだけでは不足しやすい適用条件、禁則、失敗原因を、ユーザーが明示選択した会話・行動記録で
補うと、より具体的で再利用価値のあるSkillを作れるか検証する。

単に候補数を増やすことは成功としない。次の3判断を根拠付きで行えることを目標にする。

1. 新しいSkillを作る。
2. 既存Skillの一部を更新する。
3. 一度きり、一般的すぎる、または根拠不足のためSkill化しない。

## 2. 価値仮説

同じプロジェクトの複数記録を横断すると、一つのメモだけでは見えない次の情報を直接の根拠から
発見できる。

- 繰り返し発生する問題と、その再発防止手順
- ある手順を使う条件と、使わない条件
- 最初に失敗した具体的なステップ
- 既存Skillのうち、修正が必要な指示
- 別プロジェクトでも再利用できる部分と、元プロジェクト固有の部分

この仮説が正しければ、Skill DNA Compilerは一般的な「文章からSkillを作るツール」ではなく、
経験から作成・更新・非Skill化を判断し、能力を安全に育てる製品へ進める。

## 3. 今回検証しないこと

- Vault、Codex履歴、リポジトリ全体の自動巡回
- ユーザーが選んでいない記録の読み込みまたは外部送信
- 新しい入力adapterの正式実装
- データベース移行
- Skillの自動承認、自動更新、自動出力
- Skill Graph、マーケット、複数AI向け出力
- 一般公開機能としてのUI統合

価値が確認できるまでは、既存Betaの動作と保存データ形式を変更しない。

## 4. 比較方法

同じ題材について、入力範囲だけを変えた2つの試行を行う。

### Trial A — メモのみ

- ユーザーが選んだプロジェクトメモだけを使用する。
- 現在の抽出、出典検証、DNA Traceと同じ厳格境界で候補を確認する。

### Trial B — メモと選択記録

- Trial Aと同じメモを使用する。
- ユーザーが追加で選んだ会話または行動記録だけを加える。
- 問題、最初の失敗地点、修正、検証、再発防止が分かる記録を優先する。

各Trialの正確な送信JSONと料金上限は別々に確認する。Trial Aの承認をTrial Bへ流用しない。
外部APIを使う場合は、ユーザーが内容と料金を別々に明示承認した回だけ実行する。

## 5. 比較する出力

各提案は、次のいずれかに分類する。

| 判断 | 必須理由 |
|---|---|
| `create` | 既存Skillに含まれない、複数場面で再利用できる手順がある |
| `update` | 既存Skillの特定指示へ、直接根拠のある条件・禁則・修正を加えられる |
| `no_skill` | 一度きり、一般論、プロジェクト固有、重複、矛盾、根拠不足、またはSkill以外で扱う方が適切 |

すべての提案には次を表示する。

- 判断理由
- 根拠となる文書と引用
- 複数記録での再現回数または出現範囲
- 元資料に直接書かれていない推測
- 既存Skillとの重複・更新対象
- 不確実性と追加確認事項

`create`と`update`の最終指示は、既存の厳格なDNA Trace gateを通す。`no_skill`は候補や
Skill DNAとして保存せず、実験レポートだけに理由を残す。

`no_skill`では、単に破棄するだけでなく、適切な保存先候補も区別する。

| 保存先候補 | 判断の目安 |
|---|---|
| `AGENTS.md` | プロジェクト内で常に守る恒久的な規則 |
| `Memory` | 過去の事実、ユーザーの好み、出来事 |
| `MCP` | 外部ツールやデータへの接続方法 |
| `Workflow` | 判断余地が少なく、決定的に自動化できる処理 |
| `none` | 一度きり、重複、根拠不足などで再利用資産にしない |

今回の実験は振り分けの妥当性だけを記録し、これらの形式を生成・更新する機能は実装しない。

## 6. 既存実装の再利用

- 明示選択と正確な送信範囲: 既存のVault選択とimmutable payload
- 秘密情報対策: 既存のlocal sensitive-data scanとprovider fail-closed境界
- 候補表現: `ExtractedCandidate`
- 既存Skillとの類似確認: `find_duplicate_candidates`
- 根拠検証: 既存のsource-reference validator
- 指示単位の承認: DNA Trace policy 1.0
- 利用結果: 既存の`skill_feedback`

最初の実験では、新しい永続テーブルを追加しない。`no_skill`判定とA/B比較は、機密本文を
含まないローカルJSONまたはMarkdownレポートとして保存する。価値が確認された後にだけ、
正式なdomain modelと保存契約を設計する。

## 7. 成功条件

次をすべて満たした場合だけ、製品機能化を検討する。

1. Trial Bが、Trial Aにはない直接根拠付きの適用条件、禁則、失敗原因のいずれかを1つ以上
   発見する。または、追加記録を読んでも更新不要だと根拠付きで判断する。
2. 採用候補のすべての最終指示がDNA Trace gateを通る。
3. 一度きり・一般的・重複した内容を少なくとも1件、`no_skill`として説明できる。
4. 既存Skillと重なる提案を、新規作成ではなく更新候補として特定できる。
5. ユーザーが、Trial Bの結果をTrial Aより具体的または再利用しやすいと評価する。
6. 選択していない記録、秘密情報、実メモ本文をログ・Git・共有記憶へ残さない。

候補数、文章量、AIの自信だけでは成功判定しない。

## 8. 中止・見直し条件

- 追加情報がメモの言い換えしか生まない。
- 根拠確認の負担が、得られる具体性より大きい。
- 会話固有のファイル名や一時的判断を汎用ルールとして誤採用する。
- `no_skill`判定がほとんど機能せず、何でも候補にする。
- 価値検証のためにVaultや履歴全体の自動読込が必要になる。
- DNA Traceを弱めないと候補を成立させられない。

この場合はUIやDBへ統合せず、入力の選び方、抽出指示、比較基準を見直す。

## 9. 実施順

1. 公開READMEの初回導線改善と、Ryokiさん自身の公開ZIP確認を完了する。
2. 比較対象の既存Skillを1件選ぶ。
3. Trial A用メモと、Trial Bへ加える会話・行動記録をユーザーが明示選択する。
4. 原文を変更せず、Git管理外の隔離領域へ必要な記録だけをコピーする。
5. APIを使わず、選択範囲、伏字、比較レポート形式を先に検証する。
6. 必要なら、各Trialについて正確なJSONと料金上限を別々に承認して実行する。
7. create / update / no_skill、DNA Trace、レビュー負担、実利用価値を比較する。
8. 成功条件を満たした場合だけ、最小の正式実装を別計画にする。

## 10. 実装へ進む場合の最小範囲

最初の正式実装は、既存候補一覧へ次の情報を追加する範囲に限定する。

- 提案種別: 新規作成 / 既存Skill更新 / Skill化しない
- Skill化しない場合の保存先候補: AGENTS.md / Memory / MCP / Workflow / なし
- 更新対象Skillと指示
- 複数記録にまたがる根拠
- 推測内容と不確実性

Skill更新は提案だけを作り、既存候補と同じ人間レビュー、DNA Trace、Skill DNA版更新、
出力確認を通す。`no_skill`判定は学習材料として自動反映せず、ユーザーが理由を確認できる
ローカル履歴として扱う。
